# Peiligo 项目总览

这篇文档写给:**老师、新团队成员、未来的维护者**,以及所有不写代码但需要理解这个系统的人。不需要懂 Django 或 Wagtail 也能读完;想看技术细节请继续读 [TECHNICAL_ARCHITECTURE_GUIDE.md](TECHNICAL_ARCHITECTURE_GUIDE.md)。

> 本文基于 `main` 分支当前基线整理(2026-09-02)。系统品牌名统一为 **Peiligo**(后台标题「Peiligo 内容管理」)。

---

## 1. 项目是什么

Peiligo 是一个**校园统一信息与资源检索平台**:学校的通知、活动、学习资料、软件工具和使用指南,统一在一个网站上发布、检索和归档。

它要解决的问题是老校园网站的常见痛点:

- **信息分散**:各部门内容散落在不同页面/栏目,没有统一入口;
- **资源查找困难**:学习资料、软件工具找不到、搜不到;
- **时效性不明确**:一条通知过没过期,读者看不出来;
- **来源和分类不统一**:谁发的、属于哪一类,没有固定口径;
- **后台维护成本高**:没有一套给各部门用的、权限清晰的内容维护工具。

Peiligo 的答案:五个固定板块 + 一个全站搜索 + 一套「部门各管各的内容、到期自动归档」的发布规则。

## 2. 这个系统给谁用

| 使用者 | 怎么用 |
|---|---|
| **学生(访客)** | **无需登录**,直接浏览、搜索、筛选所有已公开发布的内容;发现错误可通过页脚的统一反馈邮箱报告。没有注册、评论、报名等功能 |
| **部门工作人员** | 通过后台(`/admin/`)维护**本部门**负责的内容。每个部门一个岗位账号,只能看到和操作自己部门的内容,部门之间互不可见、互不可改 |
| **总管理员** | 全站只有一位:管理账号与板块、维护首页运营位、处理跨部门纠错、内容下架与**永久删除** |
| **技术维护人员** | 负责部署、备份、监控、故障恢复。日常不参与内容编辑 |

角色与权限的正式定义见 [../ROLE_PERMISSION_MATRIX.md](../ROLE_PERMISSION_MATRIX.md)。

## 3. 五大板块

全站内容固定为五个板块(名称与顺序冻结,见 [../INFORMATION_ARCHITECTURE.md](../INFORMATION_ARCHITECTURE.md)):

| 板块 | 网址 | 典型内容 |
|---|---|---|
| **校园纪事** | `/chronicle/` | 校内新闻、通知公告、纪事文章 |
| **校园活动** | `/events/` | 讲座、比赛、社团活动等带开始/结束时间的活动信息 |
| **学习资料** | `/materials/` | 课件、讲义、题库等可下载的学习资料(按学科、资料类型分类) |
| **软件与工具** | `/software/` | 教学软件、工具的介绍与官方下载链接(不托管安装包本身) |
| **校园指南** | `/guide/` | 办事流程、规章制度解读、新生指南等长期有效的说明文 |

每个板块都有「当前内容」列表和一个「历史归档」页(`/<板块>/archive/`),过期内容不删除,进入归档并标注「已过期」。

## 4. 核心功能(均已实现)

- **内容浏览**:首页(紧急提示、推荐位、最新通知、近期活动、板块入口)+ 五个板块列表页;
- **全站搜索**(`/search/`):关键词 + 板块 / 部门 / 类型 / 标签筛选,过期内容也纳入并标注;
- **内容生命周期**:草稿 → 预览 → 修订历史 → 发布 → 定时发布 → 到期自动归档 / 手动下线;**到期不是删除**,数据全保留,可重新发布;
- **部门权限隔离**:部门账号只能在本部门的内容子树内创建、编辑、发布、下线;任何部门账号都**没有删除权**;永久删除仅总管理员;
- **上传安全**:文档白名单(pdf/doc/docx/xls/xlsx/ppt/pptx)+ 图片白名单(jpg/png/webp),单个文件 20 MiB 上限,扩展名 + MIME + 文件内容签名三级校验,文件名清洗;
- **外链确认**:站内所有外部链接不直接跳转,先经过统一确认页(显示目标域名、来源、时间与第三方内容声明);
- **后台中文化**:Wagtail 管理界面与提示文案为简体中文;
- **治理审计**:后台「治理审计」页(`/admin/gov-audit/`)完整记录用户/组的变更;
- **登录治理**:密码最短 12 位;连续 10 次登录失败锁定 15 分钟;会话 24 小时;管理员重置密码后对方须先自行改密;
- **SEO 基础**:sitemap.xml、robots.txt、逐页 noindex 控制;
- **运行保障**(工程已就绪,见下节):健康检查、结构化日志、备份/恢复、监控信号。

## 5. 当前完成度

诚实地说,这个项目**代码已完成,但尚未上线**。分三档:

### 已完成(开发 + 生产工程)

- 五大板块内容模型、部门权限树、认证治理、治理审计、上传/外链安全、中文搜索、生命周期与归档、SEO 收口、首页运营区——全部实现;
- Docker / Compose / Caddy 生产打包、备份/恢复/监控三件套、CI 质量门——工程文件齐备;
- 本地自动化验证:pytest **604 项通过 + 269 子测试**(2026-09-02 于 `main` @ `0069953` 实测;终审时点为 574 + 266,其后新增批次又扩充了测试)、ruff 全绿、迁移无漂移(终审结论见 [../FINAL_FULL_PROJECT_REVIEW.md](../FINAL_FULL_PROJECT_REVIEW.md));
- 终审发现的 1 项 HIGH(H-1)与 2 项 MEDIUM 已在修复批次全部收口;当前无未修复的 BLOCKER/HIGH。

### 尚需验证(代码已就绪,验证未做)

- **Docker 容器实跑**:镜像构建与容器启动**尚未实际执行过**(目前仅通过 `docker compose config` 静态校验);
- **性能验证**:目标口径(核心内容 2 秒内可见、千条内容搜索亚秒、100 并发)未实测;
- **无障碍(WCAG 2.2 AA)正式验证**:代码层已按规范实现,正式走查(axe + 键盘)未执行;
- **恢复演练**:`backup_restore` 设计了严格的隔离保护,但「没演过就不算数」,需按季度演练(RTO ≤ 4 小时);
- **生产监控与备份的实际运行**:cron 接线、独立备份副本绑定等属部署现场工作。

### 尚未进行

- **真实服务器部署**(staging / production);
- **域名与 TLS 证书配置**(Caddy 具备自动申请能力,但尚未对接真实 DNS)。

## 6. 设计理念(为什么这样做)

**为什么不自己写一套 CMS?**
这个系统的本质是「内容 + 审批流 + 权限 + 附件」:草稿、修订历史、预览、定时发布、部门权限、媒体库……这些正是成熟 CMS 的看家本领。自己造等于把每个环节重写一遍,每一样都要自己为安全负责。项目冻结了一条红线:**只使用 Wagtail 官方扩展点,不修改 Wagtail 核心**——升级和安全补丁可以照常跟进。

**为什么选 Wagtail?**
Wagtail 是项目立项时确定的技术基线,它也确实合适:基于 Django(久经考验的 Python Web 框架),「页面树」的组织方式天然契合「板块 → 部门 → 内容」的校园信息结构,后台对非技术编辑友好,自带简体中文。全部 V1 需求都在官方扩展点上实现完毕,没有一处需要改核心。

**为什么学生不需要账号?**
学生只用「看」:浏览、搜索、筛选。看内容不需要身份,加注册登录只会增加使用门槛、带来隐私与账号管理负担。发现错误走页脚反馈邮箱即可。学生账号、个性化订阅列入了 V1 明确不做清单。

**为什么部门用「权限子树」而不是一张权限表?**
内容树是「板块 → 部门容器 → 内容」的层级,把部门权限挂在部门容器节点上,权限自动向子树传播——「部门只能管自己的内容」由树形结构天然成立,不需要另写一套权限判断逻辑。项目明确禁止自建权限表、JWT、按部门 ID 过滤列表这类替代方案:经验证明它们更容易留下越权口子(比如「能编辑就顺手能发布/删除」的横向越权)。

**为什么是服务器端渲染,而不是 Vue/React 单页应用?**
这是一个公开、以内容为主、低交互的网站。服务器直接出完整 HTML,搜索引擎收录(SEO)、无障碍、首屏速度、部署简单性全都更优;不需要 Node 构建链,静态资源就是纯 CSS/JS。前台也没有登录态,单页应用的交互优势用不上。

**为什么搜索先用「简单包含匹配」?**
中文搜索做过正式选型实验([ADR-0006](../adr/0006-chinese-search-backend.md)):三个候选方案在同一批真实查询上对比,最简单的「数据库包含匹配」(E1)命中率 100%、速度最快(千条内容单次查询约 9 毫秒),按「达标就用最简单方案」的预定规则胜出。将来数据量或查询复杂度上去了,还有两条更强方案(E2/E3)作为明确的升级路径。

**为什么尽量少自己造权限、认证和发布状态?**
密码强度、登录锁定、会话管理用 Django 自带机制;页面发布/下线/定时/修订用 Wagtail 原生状态机。Peiligo 的内容「五状态」(草稿/预约中/在线/已过期/已下线)**不新增任何状态字段**,全部从 Wagtail 内建状态推导而来——没有第二套状态机,就没有两套状态打架的可能。
