## 4. F-1（P2）：§21.6 默认排序契约在 E2/E3 机制上不可表达

**设计冻结口径**（§21.6 逐字）："默认排序＝`-first_published_at`（IA §9.2 #4 发布时间倒序；施加筛选不改变）。三方案均支持 queryset `order_by`（§20.0 事实 5/6）——排序契约与后端选型解耦。"组合执行＝filter-first：queryset 先过滤排序再 `.search(q)`。PS-35 同口径（"默认排序发布时间倒序"）、L727 跨类型合并排序键同依赖。

**机制真相（三段，源码＋运行时双证）**：

1. **默认调用（`order_by_relevance=True`，编译器缺省）**：PG 后端把 queryset 排序**整体替换**为相关度——postgres.py `_apply_ordering_and_scoring`：`if self.order_by_relevance: queryset = queryset.order_by(rank_expression.desc(), "-pk")`（L678-679）。即 E2/E3 默认排序＝相关度，**不是** `-first_published_at`，且无任何告警（check() 对 order_by 早退，探针 P2 亲证）。设计自己的 §20.2 差异表"相关度排序 | 无（回退 queryset 排序）| ✓（ts_rank）| ✓"其实已承认此点，却未与 §21.6"三方案一致"互相调和。
2. **官方保序机制（`.search(q, order_by_relevance=False)`）**：check() 无条件校验纯字符串排序键须为 FilterField（base.py `_get_order_by` L369-405＋`check()` L410-442，`_search()` L795 无条件调用，两后端编译器均未覆写——grep 亲证）。而 §20.1 表 A **未再声明** `FilterField("first_published_at")`（事实 2 遮蔽丢失；基类原有——事实 1/设计自登 L653 的 FilterField×14 清单内）。**运行时实证（探针）**：`Cannot sort search results with field "first_published_at". Please add index.FilterField("first_published_at") to Doc.search_fields.`——E1-fallback 与 E2/E3-postgres 两编译器**同断**（OrderByFieldError）。
3. **设计从未登记该旋钮**：全文 `order_by_relevance` 零出现（grep 亲证）；PS-32 义务集"live/expired/path＋department.slug＋各自词表"不含排序键。

**后果**：按 §21.6 照抄实现的 MB10，E1 恰好工作（fallback 保序＋check 早退），E2/E3 上要么默认相关度排序（静默违约冻结契约），要么显式保序即崩（OrderByFieldError）。"排序契约与后端选型解耦"不成立——恰与后端选型强耦合，且失败面在 D7 换方案时才暴露。

**修复（纯文档两处，零字段冲突——first_published_at 为 Page 内建列）**：①表 A 增一行 `FilterField("first_published_at")`（与 live/expired/path 同"遮蔽须再声明"理据，设计自己的表 A 标题句"缺一即遮蔽丢失"正好覆盖此遗漏）；②§21.6 增机制口径：默认排序成立须 `.search(q, order_by_relevance=False)`（三方案一致），排序键入 PS-32 义务集。探针 P6 亲证：增补该 FilterField 后两编译器 `order_by_relevance=False` 下 check() 复绿。

## 5. F-2（P3）：§20.2"FilterField 组合查询义务"E1 行运行时证伪

设计差异表（L708）："FilterField 组合查询义务 | **不需要（纯 ORM AND）** | 须声明（事实 7/PS-32） | 同 E2"；事实 7 同口径限定"**索引型**后端组合查询时…否则 FilterFieldError"。

**运行时实证（探针 P1）**：E1 fallback 编译器上 `filter(secret="x")`（未声明 FilterField 的列）＋`.search(q)` → `FilterFieldError: Cannot filter search results with field "secret"`。机制：`_process_filter` 在 `check_only=True` 下仍无条件走 `_get_filter_field_path_for_column`（base.py:234-237，check_only 仅跳过 `_process_lookup`）；`_search()` 对**所有**后端无条件调 check()（L795）；fallback 编译器未覆写（grep 亲证零 `def check`）。即 FilterFieldError 义务是**三后端同跑**的编译期闸，非 E2/E3 特有。

**影响评估**：表 A/PS-32 对五页无条件声明全部义务字段，MB10 照表 A 实现不会踩中——实际落地路径无恙；但该行位于 D7 决策依据的差异表内且极性翻转（E1 实为"须声明（同 E2/E3）"），若 MB10/PoC 阶段有人据"E1 不需要"增补表外过滤字段（如 event_is_online），组合查询即崩。修复＝§20.2 该行 E1 格改"须声明（check() 三后端同跑）"＋事实 7 去掉"索引型"限定（其引 base.py:89-201 本就是三后端共享基类）。
