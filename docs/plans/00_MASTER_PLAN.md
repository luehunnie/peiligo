- **组内总控（Orca）**：按工作组签发单步骤任务契约、执行合并、关闭步骤。
- **实现代理（Claude Code / GLM-5.3，v2.1 主工程代理）**：在单步骤对话内完成调查、普通工程决策、实现 + 自测 + 自审 + 证据压缩 + 完成报告；Claude Code 默认 `high` 推理，调整仅限当次会话。
- **独立审查者（独立 GLM 新会话）**：R1+ 步骤合并前的独立审查，一次覆盖需求/架构与实现/测试/安全双口径（§4.6）；**不得继承实现对话上下文；实现者不得担任审查者（实现者不得成为唯一审查者）**。
- **GPT-5.6 Sol（v2.1 高级决策面）**：不常驻协调、不参与每步审查；仅承担 R3/R4 高级架构与压缩风险审查、Escalation 裁决、多模态与最终高风险裁决（Senior Decision / Escalation / Final Authority）。
- **工作组**：治理组（M0.x）、架构组（M1–M7）、环境基线组（MB1）、内容与权限组（MB2–MB8）、前台与搜索组（MB9–MB10）、附件与合规组（MB11–MB14）、基础设施组（MB15–MB18）、交付组（MC1–MC8）。

### 4.2 单步骤对话边界（默认，所有步骤适用）

每步骤 = 恰好一个 Dispatch = 一个全新对话：

1. **下发**：组内总控以任务契约启动对话，契约含目标、输入文档路径、允许修改文件范围、验收命令、测试要求、完成报告格式（模板=M0.4 产物）。
2. **对话内**：实现 + 自测（验收命令在自己的 worktree 内全部通过）+ 完成报告（3 句执行摘要 + 证据路径）。
3. **结束**：`worker_done` 后对话终止；**不得在同一对话延伸到任何相邻步骤**。
4. **返工**：审查意见修复、验收失败返工必须开新对话，引用原步骤 ID 与审查报告路径；修复对话只做修复 + 回归测试，不顺带扩展。
5. **歧义处理**：遇需求歧义或前置输入缺失，用 `ask` 向上提问（PRD §26：不静默假设）。
6. **越界处理**：发现必须修改范围外文件才能完成时，停止并上报协调者重新签发契约，不自行扩界。
7. **心跳**：实现对话每约 5 分钟发送一次心跳；结束恰好一次 `worker_done`（失败步骤也发送，`--outcome failed`；schema=§4.3；命令与令牌来源约束=§4.5，仅当次对话 TASK 注入原文）。

### 4.3 完成报告与 worker_done schema（默认；v1.1 显式化，与 01 §3.2-5 同源）

完成报告 = 3 句执行摘要（做了什么/发现什么/遗留什么）+ 证据路径清单。`worker_done` 是报告的正式载体，全项目统一 schema：必填 `--subject`（短语）、`--body`（3 句执行摘要，不得为空）、`--task-id` 与 `--dispatch-id`（两者同时必填，防串话）、`--outcome`（`succeeded` | `failed`——失败只能以 `--outcome failed` 表达，不得仅写入正文）；可选 `--files-modified`（逗号分隔路径清单）、`--report-path`（长产物报告路径）。`worker_done` 恰好发送一次（§4.2-7）；命令与派发令牌仅可取自当次对话 TASK 注入原文（§4.5）。报告与审查记录入 Git 的范围按 D8 裁决（M0.3）；D8 裁决前仅落 `docs/reviews/` 与本地暂存，内容不含任何秘密（§4.5）。

### 4.4 工作树、分支与文件互斥（默认）

- M0.1 为 Git 化前唯一步骤：无 worktree，直接单文件写入。自 M0.2 起：每个实现类步骤使用独立 Git worktree + 分支（前缀见修订 12），基于 `rebuild/v1`；合并顺序按 §5 DAG，后合并方 rebase 并重跑自己的验收命令。
- **允许修改的文件范围是硬边界**；范围外文件只读。
- **共享文件清单**：`settings/*`、项目级 `urls.py`、`templates/base.html`、根依赖清单（`requirements*.txt`/`pyproject.toml`）、`.github/**`、`docs/adr/README.md`（仅状态行，v1.1——M1.2–M1.6 与 M6.3 更新其 ADR 状态行，02 原始要求）。触碰共享文件的步骤在其范围中显式标注"（共享）"；此类步骤实现可并行、**合并入 `rebuild/v1` 时按到达顺序串行**。
- 并行步骤的允许修改文件集合必须不相交（PRD §24.3）。
- 只读调查/验证类对话（如 MC2 验证、MC4 证据整理）不创建分支。

### 4.6 独立审查与风险分级（v2.1；每步骤合并前按其风险级执行）

**风险分级矩阵（R0–R4）**：

| 风险级 | 适用情形 | 实现与审查 | GPT 参与 |
| --- | --- | --- | --- |
| R0 极低 | 文档局部修改、注释、测试补充等明确小改动 | GLM 实现 + 验收命令/自动验证（免独立审查，实现者自审留档于完成报告） | 无 |
| R1 普通 | 单模块文档/代码、小功能、局部重构 | GLM 实现 + 独立 GLM Review（新会话） | 无（或仅最终摘要） |
| R2 复杂 | 跨模块、状态机、权限/发布逻辑、难 Debug | GLM `high` 推理实现 + 独立 GLM `high` Review（新会话） | 仅 Escalation |
| R3 架构级 | 公共接口、数据模型、大重构、核心架构 | GLM 调查/实现 + 独立 GLM Review + GPT 压缩 Risk/Architecture Review | GPT 审查一次 |
| R4 高影响/不可逆 | 生产、破坏性迁移、危险 Git、大面积删除 | GPT Decision + 项目负责人 Human Gate + GLM Execute | GPT 决策 + 人批准 |

**独立审查规则**：

1. R1+ 步骤：实现者 worker_done 后，由**独立 GLM 新会话**审查（**不得继承实现对话上下文**；输入 = 任务契约 + 证据包 + diff + 相关文件路径）；一次覆盖双口径——需求/架构（对照 PRD 条款与冻结 ADR 逐项核对、检查越界：改 Wagtail 核心、扩 V1、破坏权限模型、偏离信息架构）与实现/测试/安全（代码质量、测试真实覆盖——**审查者必须亲自运行验收命令与测试套件**、安全面：权限、输入校验、秘密处理、注入面）；**实现者不得担任审查者（实现者不得成为唯一审查者）**。
2. R3：在独立 GLM 审查外追加一次 GPT 压缩 Risk/Architecture Review（输入按 v2.1 §3.3 最小输入顺序：DECISION_NEEDED → GLM 建议 → 风险摘要 → 验证摘要 → `git diff --stat`；GPT 默认不读原始长日志与全量 diff）。
3. R4：GPT 决策 + 项目负责人 Human Gate 批准后 GLM 执行；§4.9 环境授权矩阵（PVE/生产逐项授权、G4 前生产禁令）全部保留并优先于本表。
4. 报告路径：`docs/reviews/<步骤ID>.review.md`（R1+ 必备）；R3/R4 的 GPT 审查另落 `docs/reviews/<步骤ID>.gpt-review.md`（修订 11，v1.3 口径）。
5. 结论 = 通过 / 有条件通过（列条件）/ 拒绝（列理由）；返工循环最多 2 轮；仍不通过 → 该步骤按 §4.8 回滚并升级项目负责人。
6. **GPT 可用性规则（FIX-02/v1.4，替代 v1.3"GPT 暂不可用条款"）**：
   - **R0**：GLM-5.3 + 自动验证/实现者自审，GPT 不参与——GPT 暂无额度不阻塞 R0。
   - **R1**：GLM-5.3 实现 + 独立 GLM 新会话 Review，GPT 不参与——GPT 暂无额度不阻塞 R1。
   - **R2**：GLM-5.3 `high` 实现 + 独立 GLM `high` 新会话 Review，GPT 仅 Escalation——GPT 暂无额度不得阻塞 R0–R2 任何步骤与门。
   - **R3**：GLM 可继续调查、Evidence 收集、PoC、方案比较与 Worker Recommendation 等非破坏性准备；但**重大架构冻结、公共接口、核心数据模型、大规模重构的正式最终裁决原则上等待 GPT Risk/Architecture Review**。GPT 不可用时**不存在全局自动替代规则**；跳过仅允许项目负责人对**一个具体 R3 Task** 发一次性 waiver，记录 `R3_GPT_WAIVER: TASK / REASON / HUMAN_APPROVAL / DATE`（该 waiver 不可复用、不可泛化）。
   - **R4**（正式生产/破坏性数据库迁移/危险 Git/大面积删除/数据丢失风险/重大权限安全操作/不可逆操作）：GPT Decision → 项目负责人 Human Gate → GLM Execute；**GPT 不可用时 R4 默认 BLOCKED**，等待 GPT 可用与 Human 批准，禁止任何全局 GPT 缺席旁路。
7. **风险级评估（FIX-09/v1.4，替代 v1.3"阶段缺省风险级"）**：风险级不按阶段无差别锁定（MB1–MB18 不再整段缺省 R2）。**每个 Task 派发时按实际改动评估**，允许凭证据上调或下调，但**硬下限不得突破**：
   - **至少 R2**：权限实现、认证安全、发布/归档状态机、附件安全、安全关键逻辑、跨模块复杂行为；
   - **至少 R3**：公共接口重大变化、核心数据模型重设计、Frozen Architecture 变化、大规模重构；
   - **R4**：正式生产、破坏性迁移、危险 Git、大面积删除、不可逆数据操作；
   - **普通级（R0/R1）**：模板页面、简单样式、普通文档、局部 SEO、简单配置、低风险测试补充——**不得仅因属 MB 阶段自动升为 R2**。
   每个任务契约必须记录 `RISK: <级别>` 与 `RATIONALE: <依据>`。既有缺省参考（可被上述逐 Task 评估覆盖）：M00=R3（G0 门一次完成 GPT 审查）；M0.x / M2 / M5 / M7 = R1；M3 / M4 = R2（权限/发布/安全核心）；M1.2–M1.6 ADR 冻结 = R3（其 GPT 审查在 G1 门合并一次完成）；MC6 = R3；MC7 / MC8 = R4（生产）；MC1–MC3 = R2 + PVE 逐会话授权；MC4 / MC5 = R1 + Human Gate（G4）。
