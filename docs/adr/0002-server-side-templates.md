## 背景

1. **产品形态**：V1 是公开、内容驱动、低交互的校园信息站点，前台无登录态（综合审计 §1 结论 2；02 §3 S1.3 论据②）。前端架构选型直接决定预览、SEO、部署、缓存、无障碍、权限一致性六个维度的实现路径长短。
2. **旧项目现状**：旧仓为 Vue 3 + TypeScript + Vite SPA（综合审计 §2.1）；该 SPA 缺少可验证的 SSR/meta/noindex 方案；Element Plus 全量引入但实际使用很少，存在体积风险（综合审计 §2.1）。旧前端搜索是拉取全量内容后的浏览器 `includes()` 过滤，不可作为 V1 站内搜索实现（综合审计 §2.1、§2.2"搜索"行）。
3. **基线差异**：旧技术基座 FastAPI/Vue 与 PRD 指定的 Wagtail/Django 基线不同（综合审计 §2.2"技术基座"行）；V1 全部前台需求均可经官方模板机制与项目代码完成，无需修改 Wagtail 核心（综合审计 §1 结论 4）。
4. **触发事件**：M1.3 步骤要求将项目负责人已确认的 C2 固化为本 ADR（00 §8 M1.3）；按 OR-4 只落 ADR，不重新选型。

## 决策

逐字固化 C2（00 §2.1，冻结不得重开）：

> **前端架构：Wagtail 服务端模板（Django 模板，无 SPA）。**

边界条件：

1. 前台所有面向学生的页面均由 Django/Wagtail 模板在服务端渲染输出 HTML；不引入 Vue/React 等前端框架作为前台架构基座，不设独立 SPA 工程与前端构建链。
2. 静态资源（CSS/JS/图片）经 Django static 体系管理；少量渐进增强脚本以独立静态文件加载，不构成 SPA。
3. Wagtail 自带管理后台为服务端渲染界面，其内置 JS 不视为 SPA 引入。
4. 旧 Vue 前端资产不得作为架构基线整体迁移，仅按审计判定选择性复用非架构层资产（综合审计 §1 结论 2）。

## 后果

**正面收益**：

1. 预览、SEO、部署、缓存、无障碍、权限一致性六维路径更短（综合审计 §1 结论 2）：Wagtail 的页面预览/修订/发布机制原生面向服务端模板；meta/noindex 由模板与页面机制直接控制，规避旧 SPA 缺少可验证 SSR/meta/noindex 方案的问题（综合审计 §2.1）。
2. 权限一致性：前台可见性与后台权限走同一服务端判定路径，避免 SPA 形态下 API 端与前端重复实现权限语义带来的越权面与漂移风险（综合审计 §1 结论 2"权限一致性"维度）。
3. 部署与运维路径短：无独立前端构建/部署链，不放大旧仓已确认的部署运维缺口（综合审计 §2.2"部署运维"行：无 CI、容器、备份、监控）。

**代价与权衡**：

1. 旧 Vue SPA 的架构层资产（路由、前端搜索、组件工程）不迁移；仅选择性复用设计令牌、a11y 模式等非架构资产（综合审计 §1 结论 2；§2.2"SEO/无障碍"行判定"部分资产可复用，能力未达标"）。
2. 前台复杂交互能力受服务端模板架构限制；V1 为低交互站点，接受此约束。

**受影响的后续步骤与产物**：M2.1/M2.2（信息架构以模板渲染为前提）；B 线模板实施步骤（后续计划）；G1 架构冻结门检查表第 2 项。

**复核时点**：G1 架构冻结门——项目负责人将本 ADR 由 Proposed 正式设为 Accepted（FIX-04 统一状态模型：Human Confirmed（C2）→ ADR 以 Proposed 落盘 → G1 设 Accepted）。此后仅当出现 V2 高交互需求（学生账号、个性化等——综合审计 §1 结论 6 列为不得进入 V1 的能力）或服务端模板成为已证实的交付瓶颈时重估。

## 替代方案

### 替代方案 1：演进旧 Vue 3 SPA（前端框架基座）

- **方案描述**：以旧仓 Vue 3 + TypeScript + Vite SPA 为基座继续演进，页面内容由前端经 API 获取并客户端渲染。
- **否决理由**：综合审计 §1 结论 2——V1 为公开、内容驱动、低交互网站，服务端模板在预览、SEO、部署、缓存、无障碍、权限一致性方面路径更短，旧 Vue 前端仍有选择性复用价值但不应成为架构基线；综合审计 §2.1——旧 SPA 缺少可验证的 SSR/meta/noindex 方案、Element Plus 全量引入存在体积风险、前端搜索为全量拉取 + `includes()` 过滤不可作为 V1 搜索实现；综合审计 §2.2——旧基座 FastAPI/Vue 与 Wagtail/Django 基线不同。
- **遗留风险**：低交互 V1 下无明显遗留；若 V2 引入高交互需求需重新评估（见"复核时点"）。

### 替代方案 2：前后端分离（独立前端工程 + Wagtail 作纯 API 后端）

- **方案描述**：新建独立前端工程（SPA 或同构框架），Wagtail 仅作为内容 API 后端供前端消费。
- **否决理由**：综合审计 §1 结论 2——同上六维路径判定，前后端分离在预览/SEO/部署/缓存/无障碍/权限一致性上路径更长，且引入双端权限与缓存语义一致性成本；治理后台方面，Wagtail 7.4 API v2 为只读接口，不足以支撑 SPA 形态的治理后台（02 §3 S1.3 论据②），在其之外补齐管理面 API 属大规模新建开发，显著扩大 V1 范围（违反 OR-5；综合审计 §1 结论 6——本轮没有需要扩大 V1 的理由）。
- **遗留风险**：放弃前后端分离在工程组织上的想象空间；V1 范围内接受。

## 合规性

1. **覆盖规则（00 §1 OR-1..OR-6）**：不违反——本 ADR 仅固化 C2，不重开选型（OR-4）；不扩大 V1 范围（OR-5，未引入学生账号、高交互等 V1 外能力）；不读写旧仓（OR-2，旧仓永久只读，本步骤仅在本 worktree 新建文档并更新索引行）；其余覆盖规则未触发冲突。
2. **已确认决策基线（00 §2）**：与 C2 一致（决策节逐字引用）；与 C1 版本组合（ADR-0001）、C4 内容载体（Page 的服务端渲染依赖本决策）兼容，无冲突。
3. **PRD §20 V1 不做清单**：不违反——本决策保持前台公开、无登录、低交互形态，未新增任何 V1 范围外能力（佐证：综合审计 §1 结论 2、结论 6）。
4. **"不修改 Wagtail 核心"约束（02 §0.2-2）**：不违反——全部前台实现经 Django 模板机制与项目代码完成（综合审计 §1 结论 4：PRD V1 未发现必须修改 Wagtail 核心的需求）。
5. **秘密纪律（00 §4.5）**：本文件不含任何秘密；提交前按 §4.5 口径执行零命中自检。
6. **决策人记录**：C2 由项目负责人确认（Human Confirmed，冻结）；本 ADR 由执行代理按 M1.3 步骤以 Proposed 落盘，状态流转决策人为项目负责人（`docs/adr/README.md` §4 硬规则，代理不得代决）。

**结论：不违反任何一条。**
