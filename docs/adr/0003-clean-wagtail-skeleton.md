## 背景

**触发事件**：M1.4 步骤（00_MASTER_PLAN §8；02 §3 S1.4）要求将项目骨架决策（已确认决策 C5 = 决策门 D2）以 Proposed 状态落盘为本 ADR，作为 G1 架构冻结门（五 ADR 之一）的批准对象与 D2 的正式裁决记录。

**问题**：重建需要一个明确的 Git 仓库与骨架起点决策——是全新起步，还是在旧实现基础上继续演进。该选择决定后续全部步骤（MB1 骨架执行及 M2–M7）的基座。

**证据与依据**（经 02 §3 S1.4 汇总转述两审计骨架比较章节，逐条可独立追溯）：

1. 旧后端实现为 FastAPI/SQLAlchemy 技术栈，与重建目标 Wagtail（Django 基座）**无共享栈**（旧站审计 `docs/audit-report-old-peiligo.md` §6；02 §3 S1.4）。
2. V1 功能对旧实现的功能覆盖率趋近零——旧实现几乎无可直接沿用的功能模块（上游审计 `docs/audit-report-wagtail-upstream.md` §4；02 §3 S1.4）。
3. **无真实数据迁移负担**（02 §3 S1.4；综合审计 `docs/PEILIGO_REBUILD_AUDIT.md` §1/§8）。
4. PRD §18（v1.4 修订后口径）：唯一执行仓库为 `peiligo_restart`；旧仓（绝对路径 `<LOCAL_PROJECT_PATH>`）永久只读即视为等效归档，不建只读标签或归档分支（00 §3 修订 15；OR-2）。
5. **前置状态**：PRE-2（旧仓归档前置）已随 00 §3 修订 6 废止——OR-2 旧仓永久只读即等效归档，无旧仓归档前置；Git 基线 = M0.2 已完成 peiligo_restart 入库（`rebuild/v1` 分支）。

**约束**：OR-1（唯一项目位置 = `<LOCAL_PROJECT_PATH>_restart`）；OR-2（旧仓及其全部 worktree 永久只读）。

## 决策

**C5 逐字引用固化**（00 §2.1，Human Confirmed，冻结不得重开）：

> 项目骨架：`peiligo_restart` 全新仓库干净 Wagtail 骨架（由 OR-1 派发指示确认；不继承旧仓任何 Git 历史/分支/工作区）。

展开为可检验的肯定句与边界条件：

1. 唯一执行仓库为**全新仓库** `<LOCAL_PROJECT_PATH>_restart`（OR-1）；骨架以 **`wagtail start` 起步**生成干净骨架，依赖版本按 C1/ADR-0001 约束在首次锁依赖时执行。
2. **不继承旧仓**（绝对路径 `<LOCAL_PROJECT_PATH>`）**任何 Git 历史、分支或工作区**（含 `feat/m4-admin-auth` 工作区现状等一切旧仓状态）；新旧仓库之间不建立任何 Git 级联关系。
3. 旧仓在本项目中的唯一角色：**永久只读，仅可用于审计与选择性复用**（复用范围 = 综合审计 §3 清单）；复用方式为从旧仓只读读取后向新仓移植，不产生任何针对旧仓的操作安排。
4. 骨架执行落点为 MB1（02 §3 S1.4 旧称 B1：`wagtail start` + 按域拆 app），**本 ADR 仅固化决策**，本步骤不执行任何骨架生成或仓库分支操作（单步骤对话边界）。
5. V1 范围以 PRD 为准不得扩大（OR-5）；本决策不引入 V1 外任何功能。

## 后果

**正面收益**：

- 干净基座，零历史包袱：不受旧仓分支/工作区状态（含工作区不干净现状）影响，旧仓任何状态均不阻塞本项目步骤（OR-2）；
- 与 C1（Wagtail 7.4.x LTS + Django 5.2 LTS + Python 3.13）、C2（服务端模板）直接对齐，`wagtail start` 提供官方脚手架的安全缺省配置；
- 审计与选择性复用通道保留：旧仓仍可按综合审计 §3 清单只读取用；
- 决策门 D2 以本 ADR 为正式裁决记录，G1 门批准即闭环。

**代价与权衡**：

- 放弃对旧仓实现代码的直接沿用：一切复用须走"选择性复用"通道（按综合审计 §3 清单逐项判断），多数功能需在干净骨架上重写；
- 旧仓中未列入复用清单的实现资产不再进入新仓。

**受影响的后续步骤与产物**：

- MB1（骨架执行）：按 `wagtail start` + 按域拆 app 执行；上游审计 §4 的 app 拆分建议（`notices`/`resources`/`guides`/`departments`/`frontend` 等）作为其输入引用；
- 断言（测试要求，02 §3 S1.4）：**MB1 骨架 app 划分必须与本 ADR 引用的拆分建议一致，或记录偏离理由**；
- M2–M7 全部步骤均以该骨架为基座；G1 门批准后本 ADR 转 Accepted。

**复核时点**：G1 架构冻结门（M1.6 后，项目负责人批准即转 Accepted）；此后仅当 OR-1/OR-2 覆盖规则或综合审计 §3 复用清单发生变更时，由项目负责人决定是否重开本决策，代理不得自行重评。

## 替代方案

1. **路径 A：在旧仓原结构上重构演进**——已否决。否决理由：等于重开已冻结的技术基线（C1–C5，OR-4）；旧栈 FastAPI/SQLAlchemy 与 Wagtail 基座无共享栈，重构成本高于重建；且与 OR-2 直接冲突（旧仓永久只读，本项目不在旧仓进行任何演进）。遗留风险：无。
2. **克隆旧仓后删减（fork-and-prune）**——已否决。否决理由：仍继承旧 Git 历史，违反 C5 明文"不继承旧仓任何 Git 历史/分支/工作区"；且携带冗余分支与工作区状态，审计与清理负担大于收益。遗留风险：无。
3. **不经 `wagtail start`、手工从零搭建 Django/Wagtail 项目**——已否决。否决理由：偏离 C5/M1.4 明文"`wagtail start` 起步的干净骨架"语义，放弃官方脚手架的安全缺省配置，徒增基线风险且无对应收益。遗留风险：无。
