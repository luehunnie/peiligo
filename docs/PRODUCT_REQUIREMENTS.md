## 1. 文档目的

本文档记录 Peiligo 重建项目已经确认的产品边界、角色、内容结构、功能要求、非功能要求和验收标准，作为 V1 的需求基线。

基线确认后，任何新增需求默认进入后续版本候选池。只有项目负责人可以批准其进入 V1。开发代理、工作组、学校部门和技术总控不得自行扩大范围。

## 2. 产品定位

Peiligo 是面向校内学生的非商业信息资源检索网站。学生无需登录即可浏览公开内容，重点解决以下问题：

1. 快速查看仍然有效的最新通知及截止事项。
2. 通过关键词、板块、内容类别或发布部门查找权威信息。
3. 查询校园生活中的长期固定信息，例如开放时间、地点和联系方式。
4. 获取校园活动、学习资料以及软件与工具的可信介绍和外部资源入口。

V1 优先服务桌面浏览器。学生前台在手机浏览器上仍须能够正常阅读、搜索和筛选；后台管理界面不保证完整的手机端体验。

## 3. 产品原则

- 重新确认需求，不照搬旧站历史结构。
- 用户价值证据优先；证据不足时由项目负责人最终裁决，并记录为待验证假设。
- 学生前台公开、无需账号；账号只供网站管理人员和部门信息岗位使用。
- 采用简单、清晰的发布治理，不为 V1 建设复杂审批系统。
- Wagtail 作为上游开源框架依赖；优先使用官方扩展机制。
- 修改 Wagtail 核心必须证明官方扩展点无法满足需求，并单独记录 ADR、补丁范围及回归测试。
- AI 工作流只用于审阅和组织开发流程，不属于网站产品功能。
- 可访问性、内容权威性、时效性和可检索性优先于装饰性功能。

## 4. 用户与角色

### 4.1 学生访客

- 无需登录。
- 可查看、搜索、筛选所有已公开发布的内容。
- 不具备投稿、评论、报名或个人订阅能力。
- 可通过统一工作邮箱报告错误信息、失效链接或版权问题。

### 4.2 总管理员

V1 仅设置一名总管理员，负责：

- 网站基础配置、账号和板块管理。
- 创建、停用和重置部门岗位账号。
- 管理首页重要内容与置顶内容。
- 处理跨部门纠错、内容下架和永久删除。
- 维护无法由责任单位自行维护的校园固定信息。
- 定期检查统一工作邮箱中的投稿与纠错信息。

总管理员同时承担简化后的内容治理职责。V1 不单独设置校级审核员。

### 4.3 部门岗位账号

- 每个部门最多设置一个岗位账号。
- 账号属于岗位，不属于个人；同一时间只允许当前负责人使用。
- 人员变更时办理交接，并立即重置凭据。
- 只能创建、编辑、发布、下线和归档本部门内容。
- 不得修改其他部门内容、网站配置、账号、板块或首页置顶状态。
- 前台只显示部门/单位名称，不显示登录用户名或具体操作人员姓名。

### 4.4 技术维护人员

由项目负责人或其指定人员负责：

- 依赖升级、安全修复和故障恢复。
- 备份检查与恢复演练。
- 测试、预发布和生产环境维护。
- 运行监控与技术交接文档。

技术维护与日常内容管理是不同职责。

## 5. 权限与登录

- 使用 Wagtail/Django 自带的认证和权限体系，不自建独立用户中心。
- 不开放公开注册，不建立学生账号。
- 首版只使用用户名和密码，不强制多因素认证。
- 部门账号密码可由总管理员重置。
- 密码重置后必须强制修改密码；不得使用长期统一默认密码。
- Wagtail 管理后台仅允许从校园网或学校 VPN 访问。
- 管理后台必须使用 HTTPS、登录限速和强密码策略。
- 内容修改使用 Wagtail 自带的基础修订历史，记录操作者和时间。

## 6. 信息架构

网站包含五个一级板块：

1. **校园纪事**
2. **校园活动**
3. **学习资料**
4. **软件与工具**
5. **校园指南**

板块描述“信息是什么”，部门字段描述“谁发布”。任何部门均不建立独立主页。

部门名称作为内容作者元数据展示，并可用于搜索结果筛选；部门筛选结果不是部门主页。

## 7. 内容模型

### 7.1 通知

- 通知只能归入“校园纪事”或“校园活动”。
- 必须包含标题、摘要、正文、所属板块、发布部门、发布时间和有效期。
- 可包含图片、附件、外部链接和受控标签。
- 默认按发布时间倒序展示。
- 到期后自动退出首页和默认列表，但保留在历史归档及站内搜索中。
- 支持预约发布。

### 7.2 文章

- 用于校园纪事和校园活动中的长期阅读内容。
- 必须包含标题、摘要、正文、所属板块、发布部门和发布时间。
- 可包含图片、附件、外部链接和受控标签。
- 支持预约发布，不默认设置下线时间。

通知与文章是两种独立内容类型，不通过单一模型强行混用。

### 7.3 校园活动

活动内容必须支持结构化字段：

- 开始时间与结束时间。
- 活动地点；线上活动可标记为“线上”。
- 报名链接（可选）。
- 活动状态：即将开始、进行中、已结束。

报名跳转至外部系统，V1 不提供站内报名。

### 7.4 学习资料

学习资料使用以下受控维度分类：

- 学科或专业方向。
- 资料类型。
- 关键词标签。

V1 不建立课程、教师和学期之间的复杂课程库。

### 7.5 软件与工具

每条内容至少包含：

- 软件或工具名称。
- 用途说明。
- 适用平台。
- 来源链接或第三方网盘链接。
- 授权或费用说明。
- 发布时间或最后更新时间。

网站原则上不直接托管软件安装包。资源通过外部网站或第三方网盘访问。

所有下载、网盘及第三方资源链接必须经过统一确认跳转页。跳转页显示目标域名、资源来源、发布时间或最后更新时间，以及第三方内容可能变化的声明。无需强制勾选免责协议。

V1 不主动巡检第三方链接，也不开发自动爬虫；仅在收到反馈或管理员发现问题时更新。

### 7.6 校园指南

用于面向全校的生活和办事固定信息，例如澡堂、食堂、场馆、服务地点与开放时间。

统一字段包括：

- 服务名称。
- 指南类别。
- 地点。
- 开放时间。
- 联系方式。
- 补充说明。
- 责任来源或责任单位。
- 维护方式。
- 最后确认日期或更新时间。

可使用后台的责任部门自行维护其信息；无法或不愿使用后台的单位通过统一工作邮箱投稿，由总管理员更新。

总管理员每月检查工作邮箱，每学期集中复核全部固定信息。高频变化内容可设置更短的人工复核周期。V1 不开发复杂自动提醒。

### 7.7 富文本与页面组件

- 使用受控内容模块组合标题、正文、图片、附件、表格等内容。
- 普通部门账号不得输入任意 HTML 或 CSS。
- 所有组件必须符合统一视觉规范、响应式要求和无障碍要求。
- 优先通过 Wagtail `StreamField` 等官方能力实现，最终结构由技术审计确定。

## 8. 发布、归档与纠错

- 部门岗位账号发布本部门普通内容时无需审批。
- V1 不建设提交、审核、退回、二次确认等复杂流程。
- 只有总管理员可以设置全站重要内容或首页置顶。
- 部门如需置顶，通过统一工作邮箱申请。
- 内容默认下线或归档，不直接永久删除。
- 通知到期自动归档；文章和资源可由部门手动下线。
- 永久删除仅由总管理员执行，适用于测试数据、违法内容或明确无保留价值的记录。
- 学生发现内容错误、链接失效或侵权问题时，通过每页提供的统一工作邮箱反馈。
- 邮件链接应自动带上内容标题和页面地址。

## 9. 首页与导航

首页信息优先级如下：

1. 紧急或重要提示。
2. 最新且仍有效的通知。
3. 近期校园活动。
4. 五个一级板块入口与其他内容。

首页主体自动展示最新内容；总管理员可管理数量固定、具有开始与结束时间的推荐位或置顶位。

## 10. 搜索与筛选

站内搜索至少覆盖：

- 标题与正文。
- 五个板块。
- 内容类型。
- 发布部门。
- 受控类别和标签。
- 校园指南的结构化信息。

搜索结果支持按板块、部门和类别筛选，并提供清晰的无结果提示。

首版优先评估 PostgreSQL 与 Wagtail 自带搜索能力。中文搜索效果必须通过真实数据验证；只有验证不达标时才评估独立搜索服务。

## 11. 附件与外部资源

- 允许上传 PDF、Office 文档和常见图片。
- 设置文件类型和大小限制，并检查危险扩展名与伪造 MIME 类型。
- 禁止上传密码、个人敏感信息、成绩名单等不应公开的数据。
- 外部资源应优先链接官方或可信来源。
- 不得在未获校方明确批准前，将真实破解版软件链接加入测试、预发布或生产数据。
- 收到版权或安全投诉时，总管理员可立即隐藏相关内容，保留内部处理记录，核实后决定恢复或删除链接。

免责声明不能代替版权授权和安全审查。软件资源的最终允许范围属于校方、带队老师和团队共同决定的上线决策门。

## 12. 前台访问、SEO 与隐私

- 学生前台通过公网公开访问，无需登录。
- 默认允许搜索引擎收录，单篇内容可设置 `noindex`。
- 站内不得发布个人敏感信息或面向内部的保密材料。
- 收集匿名且最小化的页面访问、搜索词、无结果搜索和筛选使用数据。
- 不建立学生画像，不记录个人浏览历史，不使用广告追踪。
- 分析工具优先考虑校内自托管。

## 13. 视觉、响应式与无障碍

- 严格遵循学校现有视觉识别规范。
- 旧 `peiligo` 前端仅作为审计和复用候选，不自动成为设计基线。
- 采用桌面优先设计。
- 学生前台在手机端必须支持正常阅读、搜索和筛选。
- 后台管理以桌面 Chrome/Edge 为重点验收环境。
- 前台正式目标为 WCAG 2.2 AA。
- 支持当前及前一个主要版本的 Chrome、Edge、Firefox 和 Safari；不支持 Internet Explorer。
- V1 仅提供简体中文，但不得用难以迁移的方式写死多语言结构。

## 14. 性能目标

在学校正常网络、接近正式环境的数据量和常用桌面设备下：

- 主要页面核心内容约 2 秒内可见。
- 普通搜索请求约 1 秒内返回。
- 首页图片、附件预览和前端脚本必须受到约束。

具体测量方法和数据规模在技术设计阶段确定。

## 15. 数据、存储与备份

- 正式数据库使用 PostgreSQL。
- 开发和测试环境尽量使用同类数据库，避免依赖 SQLite 特性。
- 首版媒体文件存储于服务器本地磁盘，通过 Django 存储接口访问，不写死本地路径。
- 数据库与媒体文件必须配套备份。
- 每日自动备份，最多接受 24 小时数据损失。
- 定期执行恢复演练；重要版本发布前额外备份。
- 审计日志至少保留一年。

## 16. 环境与部署

- 至少区分本地开发、测试/预发布、正式生产三个环境。
- 校园网 PVE 主机只用于测试/预发布，不是生产环境。
- PVE 中统一使用 Ubuntu 虚拟机及 Docker 部署网站服务。
- 飞牛系统不承载应用运行；可另行评估是否作为备份存储。
- 正式环境将在另一台学校服务器上部署，具体条件待确认。
- 应用必须容器化、配置外置，并保持可迁移。
- 测试与生产不得共享数据库、媒体目录、密钥或域名。
- 允许在公告后的维护窗口短暂停机，不要求 V1 零停机。
- 目标是在故障后 24 小时内恢复服务。

## 17. 监控与维护

首版至少监控：

- 服务存活。
- 应用错误。
- 磁盘空间。
- 数据库与媒体备份结果。
- 异常登录行为。

日志不得记录密码或敏感附件内容。

每月检查 Wagtail、Django 和前端依赖的安全更新；普通升级按季度评估，并先在预发布环境验证。

## 18. 旧站与重建策略

> 本节仓库归属表述已于 2026-08-18 经项目负责人授权修订（治理一致性修复 v1.4）：V1 唯一项目仓库为全新仓库 `peiligo_restart`；旧 `peiligo` 仓库设为永久只读禁区（不对其实施任何 git 写操作），即视为等效归档，不另行建立只读标签或归档分支。其余策略不变。

- 正式代码使用全新仓库 `peiligo_restart`（2026-08-18 修订；原表述"继续使用现有 `peiligo` 仓库"废止）。
- 旧 `peiligo` 仓库永久只读（等效归档；原表述"在重建开始前为旧实现建立只读标签或归档分支"废止——2026-08-18 修订）。
- 新版本在 `peiligo_restart` 的重建分支 `rebuild/v1` 开发，完成试运行和验收后合并回 `main` 并打 `v1.0.0` 标签（2026-08-18 修订；替换主分支的动作在本仓库内完成）。
- 旧站没有真实业务内容，填充测试数据不迁移到新系统。
- 旧前端是复用候选，必须先审计技术栈、依赖、耦合、响应式、无障碍、性能和维护成本。
- 审计报告将旧前端内容分类为“直接复用、改造复用、重新实现”。
- 审计后比较两条路径：在旧项目结构内重构，或建立干净的 Wagtail 项目骨架；该决策已确认为"全新仓库内干净骨架"（见 §19 第 3 项）。

## 19. 待审计的技术决策门

以下事项截至 2026-08-18 的状态：第 1、2、3 项已由项目负责人确认（决策记录 C2、C1、C5，表述见各条；技术内容未改动）；第 4–7 项尚未裁决，仍不得由开发代理自行决定：

1. **前端架构**——已确认（C2）：**采用 Wagtail 服务端模板方案**。原比较口径（前后端分离 vs 服务端模板的部署、API、预览、缓存和无障碍成本）留作决策依据记录。
2. **Wagtail 版本**——已确认（C1）：**Wagtail 7.4.x LTS + Django 5.2 LTS + Python 3.13**（依赖钉版区间与补丁复核节奏由架构 ADR-0001 固化）。
3. **项目骨架**——已确认（C5，2026-08-18）：**在全新仓库 `peiligo_restart` 建立干净的 Wagtail 项目骨架**（不继承旧仓 Git 历史；原"原结构重构 vs 同仓库新骨架"的决策门以"全新仓库干净骨架"裁决关闭）。
4. **中文搜索**：验证 PostgreSQL/Wagtail 搜索质量，再决定是否需要扩展或独立搜索服务。
5. **生产服务器**：待学校提供正式生产环境约束后确定反向代理、证书、备份位置与资源规格。
6. **仓库最终可见性**：学校、带队老师和团队共同决定是否公开；决定前按私有仓库管理。
7. **软件资源合规范围**：校方书面确认是否允许特定第三方资源；确认前只使用官方、开源或已授权示例。

## 20. V1 明确不做

- 学生账号、注册和个性化推荐。
- 邮件、微信公众号或其他面向学生的主动推送。
- 复杂内容审批流。
- 在线报名、申请、缴费或材料提交。
- AI 自动写作、自动分类、自动审核或自动发布。
- 原生手机 App。
- 多语言内容发布。
- 部门独立主页。
- 评论、点赞、收藏和学生投稿。
- 自动检查第三方网盘或资源链接。

## 21. V1 核心验收场景

V1 必须满足以下端到端场景：

> 一名学生无需登录，在桌面浏览器打开网站，能快速看到仍有效的最新通知，并通过关键词、板块、部门或类别找到所需通知及校园固定信息；部门岗位账号能独立发布和维护本部门内容。

主要验收项：

- 学生无需登录即可完成核心浏览和搜索任务。
- 通知有效期、自动归档和排序符合规则。
- 活动状态能根据时间正确展示。
- 部门账号只能管理本部门内容。
- 总管理员可以管理账号、栏目、置顶和纠错。
- 软件与资料外链经过确认跳转页。
- 校园指南使用统一结构化字段。
- 手机端可完成前台基本阅读、搜索和筛选。
- WCAG 2.2 AA 必须项通过检查。
- 性能目标在约定测试环境中达成。
- 备份与恢复流程经过验证。

最终产品验收由项目负责人独立批准。

## 22. 试运行与正式上线

- 先由总管理员和 1–2 个部门试运行。
- 试运行期建议为 2 周。
- 期间至少完成真实发布、修改、搜索、归档和固定信息更新场景。
- 试运行期间只修复缺陷；新增想法进入需求候选池。
- 通过验收后再创建其他部门岗位账号。
- 正式上线前必须录入并核验核心校园固定信息、部门来源数据和一批真实通知。
- 测试填充内容、默认账号和测试附件必须从正式环境移除。

## 23. 自动化测试与合并门禁

核心内容模型、权限、发布、归档、搜索和关键页面必须具备自动化测试，尤其覆盖：

- 部门账号不能修改其他部门内容。
- 通知到期后自动归档。
- 只有总管理员能管理账号和首页置顶。
- 外部资源链接经过确认跳转页。
- 未发布或已下线内容不会公开展示。

CI 必须自动运行：

- 后端测试。
- 前端测试与构建。
- 代码格式和静态检查。
- 依赖及基础安全检查。
- 关键无障碍检查。

全部门禁通过后才能合并步骤分支。

## 24. 开发组织与代理治理

### 24.1 总控（Orca）

- 只管理需求基线、任务 DAG、工作组边界、决策门、验收和结论汇总。
- 不直接编写业务代码。
- 无权自行扩大产品范围。
- 不承担每步审查（v2.1：审查按 §24.3 风险分级执行）。

### 24.2 大步骤工作组

- 每个大步骤建立独立工作组，由一个组内总控（Orca）管理。
- 组内每个下级代理对话只负责一个可验收步骤，完成后结束。
- 每个步骤必须明确单一目标、输入文档、可修改文件范围、验收命令和完成报告。
- 后续步骤必须建立新对话，不允许原对话自行延伸任务。

### 24.3 实现与审查（v2.1 治理口径）

- 组内总控（Orca）定义任务契约和验收要求。
- Claude Code 负责主要实现；计划使用团队配置的 GLM-5.3 模型（默认 `high` 推理）。
- 按风险分级 R0–R4 执行审查：普通步骤由独立 GLM 新会话审查，一次覆盖需求/架构与实现/测试/安全双口径；架构级步骤另加 GPT 压缩风险/架构审查；高影响操作由 GPT 决策加项目负责人批准后执行。
- GPT 定位为高级决策、升级裁决与最终高风险裁决，不常驻协调、不逐步审查。
- GPT 不可用时的处理（2026-08-18 修订）：R0–R2 步骤与门不受影响；R3 重大裁决原则上等待 GPT 可用，项目负责人可对一个具体 R3 任务签发一次性豁免记录（含任务、理由、批准人、日期，不可复用、不可泛化）；R4 默认阻塞，直至 GPT 可用并获项目负责人批准。不存在全局自动旁路。
- 实现者不能作为唯一审查者；独立审查不得继承实现对话。
- 不允许两个代理并发修改同一文件集合。

### 24.4 工作树与阶段门

- 每个可交付开发步骤使用独立 Git worktree 和分支。
- 只读调查任务不创建无意义分支。
- 前一个大步骤未通过验收时，后续依赖步骤不得开始。
- 只有互不依赖、不会写入共享文件的调查任务可以并行。
- 需求基线通过后才能冻结架构；架构与内容模型通过后才能进入主要开发。
